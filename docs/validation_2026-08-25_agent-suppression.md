# 파이프라인이 안 돌던 진짜 이유 — 하네스가 Agent 호출을 막는다 (2026-08-25)

## 결론

**스킬 SKILL.md 가 "Agent 도구로 호출"이라고 지시해도 하네스가 그것을 막는다.**
헤드리스 세션 프롬프트에 다음이 박혀 있다.

```
Do not call the AgentTool unless the user requested it
```

스킬 절차의 지정은 "사용자 요청"으로 간주되지 않는다. 그래서 `humanize-monolith` 가
한 번도 안 불렸고, `final.md` 가 없으니 Phase 2.5 게이트도 가리킬 대상이 없었다.
게이트 배선을 고쳐도 안 고쳐졌던 이유가 이것이다.

## 실측

같은 입력(`fx_guard_overedit`, 308자), 프롬프트만 다르게.

| 조건 | 회차 | `Task` 호출 | 게이트 실행 | 변경률 | 가드 초과 |
|---|---|---|---|---|---|
| 기존 러너 프롬프트 | 11 | **0/11** | **0/11** | 0.414~0.667 | 6/11 |
| 서브에이전트 호출을 **명시 요청** | 3 | **3/3** | 2/3 | **0.266~0.386** | **0/3** |

명시 요청 프롬프트에 넣은 문장은 이것 하나다.

> 스킬 절차대로 humanize-monolith 서브에이전트를 Agent(Task) 도구로 호출해서 처리하고,
> Phase 2.5 변경률 게이트도 반드시 실행해줘.

## 딸려 나온 것 — 과윤문은 파이프라인 부재의 증상이었다

명시 조건에서 변경률이 **0.266~0.386 으로 떨어지고 3/3 전부 가드를 통과한다.**
명시 없을 때는 0.414~0.667 로 절반 넘게 초과했다.

즉 `fx_guard_overedit` 가 8일 넘게 붉었던 것은 스킬이 과윤문해서가 아니라
**파이프라인이 아예 안 돌아서**다. monolith 서브에이전트가 `보수` 강도 지시를 받고
고치면 변경률이 저절로 낮아진다. 인라인으로 혼자 고칠 때만 넘친다.

이것으로 앞선 두 판정이 모두 정리된다 — fixture 상한 0.5 는 옳았고(참조 출력 0.481),
스킬도 가드를 어기고 있지 않았다. **어긴 적이 없는 게 아니라, 검사받을 파이프라인이
시작조차 안 했다.**

## 등록 계층은 무관하다 (확인함)

- `~/.claude/agents/humanize-{monolith,diagnostician,finalizer}.md` 심링크 3종 정상
- `~/.claude/skills/humanize-korean` 심링크 정상
- `settings.json` 에 비활성화 설정 없음
- 세션 도구 목록 255종에 `Task` 포함

**토글이나 재설치로 고쳐지지 않는다.** 실제로 토글 후 재측정했으나 0/1 로 동일했다.

## 볼트 문서 한 줄이 틀렸다

볼트 `.claude/CLAUDE.md` 는 "요청으로 간주"에 이렇게 적어 뒀다 —
*발동된 스킬 절차가 서브에이전트를 지정한 경우*. **이 하네스에는 그런 예외가 없다.**
우리 쪽 해석이었고, 실측이 반증했다.

## 처방

`tests/humanize_runner.py` 의 `_prompt()` 에 둘을 넣는다.

1. 서브에이전트 호출을 **명시 요청**으로 적는다
2. **"파일은 만들지 마"를 뺀다** — Phase 2.5 는 파일 기반이라 이 구절이 게이트를 죽인다
   (Bash 0회 대 5회로 확인, n=1)

⚠️ 이것은 **테스트 하네스만** 고친다. 실사용에서도 같은 억제가 걸리면, 스킬을 부르는
사람이 매번 "에이전트 써서"라고 말해야 파이프라인이 산다. 그건 스킬 설계 쪽 문제다.
