# 게이트 배선 수리와 그 결과 — 2026-08-25

## 무엇을 고쳤나

`verify_gates.py` 가 임의 경로 두 개로 정상 동작함을 먼저 실증했다(임시 파일로 참조
출력을 넣어 exit 1, WARN 48.1%). 그러니 스크립트는 멀쩡하고 고칠 곳은 SKILL.md 였다.

코덱스에 발주해 둘을 고쳤고, 1차 산출물의 설계 문제 셋을 되돌려 2차에서 정리했다.

| | 1차 | 2차(채택) |
|---|---|---|
| 게이트 호출 | 22줄 블록을 네 곳에 복제 | 각 경로에 한 줄, 상세는 Phase 2.5 한 곳 |
| 본문 전달 | heredoc 에 `{원문 전체}` 인라인 | Write 도구로 임시 파일에 저장 |
| exit 처리 | `exit "$gate_status"` | `echo "gate_exit=$?"` |

되돌린 이유는 각각 이렇다. 복제는 이 레포에 전례가 있다 — 정규식 `[A-K]` 를 두 파일에
하드코딩해 두고 L절을 만들었을 때 **오류 없이 절을 통째로 스킵**했다. heredoc 인라인은
Standard, Heavy 가 1만자급을 단일 콜로 처리하므로 길이와 구분자 충돌 양쪽에서 깨진다.
`exit` 는 게이트의 exit 1, 2 를 **도구 호출 실패로 보이게** 만드는데, 그 둘은 정상
신호이지 실패가 아니다.

`tests/test_skill_gate_wiring.py` 를 추가했다 — 세 경로 각각에 `verify_gates.py` 를 부르는
명령이 있는지, Phase 2.5 에 mktemp 폴백 서술이 있는지 단언한다. 245 passed, 1 skipped.

## 왜 — 내가 겨눈 고리가 틀렸다

도구 호출을 따라가면 스킬이 어디까지 가는지 보인다.

```
Skill: humanize-korean
Bash:  SKILL_ROOT 해석
Bash:  ls _workspace/...
Write: _workspace/2026-08-25-001/01_input.txt
Read:  quick-rules.md
Bash:  mktemp -d
Write: /tmp/humanize-.../before.txt      <- 여기서 멈춘다
```

`before.txt` 는 쓰는데 `after.txt` 가 없다. **윤문본이 아직 존재하지 않기 때문이다.**

수리 전후 8회를 통틀어 **`Task` 도구 호출이 0회**다. `humanize-monolith` 서브에이전트가
한 번도 안 불린다. 스킬은 `quick-rules.md` 를 읽고 **자기가 직접 고쳐 버린다.** 그러면
`final.md` 도 없고 게이트가 가리킬 "after" 도 없다.

`Task` 가 없어서가 아니다 — 세션 init 레코드의 도구 목록 255종에 `Task` 가 들어 있다.
있는데 안 쓴다.

## 그래서 진짜 결함은 이것이다

**헤드리스 단일 프롬프트에서 스킬의 파이프라인이 아예 실행되지 않는다.** monolith 콜이
없으니 산출물이 없고, 산출물이 없으니 게이트도 없다. 게이트 배선은 그 뒤에 있는 고리였고,
내가 고친 것은 이미 도달하지 못하는 지점이었다.

이것이 사실이면 `tests/test_humanize_live.py` 는 **스킬을 시험하고 있지 않다.** 모델이
`quick-rules.md` 를 읽고 얼마나 잘 고치는지를 잴 뿐이다. `fx_guard_overedit` 의 붉음은
가드 불이행의 증상이 아니라 **파이프라인 부재의 증상**이다.

⚠️ 이 판정의 범위: 입력 1종(308자), 프롬프트 1종, 회차 8회다. **입력이 짧아서 스킬이
단축한 것인지, 헤드리스라서 그런 것인지 아직 안 갈랐다.** 긴 입력과 대화형 세션을 각각
재 봐야 확정된다.

## 수리 자체는 남긴다

게이트 배선은 이제 복제가 없고 exit 처리가 옳다. 파이프라인이 도는 경로(대화형 세션,
긴 입력)에서는 이 수리가 유효하다. 다만 **"이것으로 fx_guard_overedit 가 초록이 된다"고
기대하지 말 것.**
